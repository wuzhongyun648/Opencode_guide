# Harness 系列审核与归档要求

## 1. 审核门槛

每篇主系列文章都必须经过以下检查后才能视为完成：

### 学习主线审核

- 开头的问题是否能被初学者理解。
- 直观答案是否先于实现细节出现，并自然进入正文，而不是额外制造一层模板标题。
- 贯穿场景是否真的解释了本章机制，而不是装饰或动手任务。
- 读者是否能在结尾回答本篇唯一主问题。
- 二级标题是否对应独立认知主题，三级与四级标题是否正确表达其组成、步骤或分支；复杂长文需要时是否使用 `1.1.1` 继续展开，而不是把多个机制挤在一个 `1.1` 下。不得用固定数量反推文章结构。
- 主系列 H2 是否按“一、二、三”连续编号，H3/H4 是否分别按 `1.1`、`1.1.1` 在父级内连续编号且前缀匹配；是否混入未编号 H2、跳号、孤立的单个 H4，或修改标题后失效的“第 X.Y 节”引用。
- 是否存在“正文、总结、补充分类、表格、再次总结”的重复编排。

### 关系与详略审核

- 顺序关系是否使用流程或步骤，而不是伪装成平级知识点。
- 并列关系是否位于同一父级；互斥方案是否标明选择条件。
- 从属内容、误解和补充边界是否留在所属主题内。
- 核心因果链是否获得最多篇幅，次要边界是否明显更短。
- 重编排是否保留旧稿中有教学价值的机制、边界和解释，而非为了减少标题而缩减内容。
- 是否删除了独立动手任务、Prompt 操作、预期现象和完成条件，只保留用于解释架构的案例轨迹。

### 架构与去重审核

- 内容是否属于该篇在 `01_Series_Architecture.md` 中的所有权。
- 与其他篇重复时，是否保留主讲处并改为链接。
- 是否区分 Model、Agent、Harness、Tool、Session 和 Client。
- 是否区分模型决策与 Harness 的确定性控制。

### 事实审核

- 当前默认行为是否由固定源码或测试支撑。
- 正文中的关键代码是否来自固定源码，节选是否保留了理解控制关系所需的上下文。
- 是否把设计文档、规划或 native V2 能力误写成默认行为。
- 是否区分 Permission 与 OS Sandbox。
- 是否区分 durable、process-local 和 live-only 状态。
- 源码标识、文件和链接是否有效。

### 编辑审核

- 不出现研究任务编号、过程状态和无关测试日志。
- 标题层级、表格、代码块和相对链接正确。
- 术语首次出现有解释，后续使用一致。
- 没有依赖并发 Bug 等超出目标读者背景的案例。
- 没有为了形式统一，让所有小节呈现近似篇幅。
- 没有把关键源码全部推到附录，也没有用源码列表代替解释。

## 2. 审核方式

- 起草者先自审结构与事实。
- 非起草者进行交叉审核，重点检查重复、跳步、内容缩水、源码事实和错误归属。
- 主负责人最后通读整套系列，统一术语、导航、案例和结论。
- 使用脚本检查 Markdown 链接、标题、旧文件引用和禁止出现的研究过程词。

## 3. 旧材料归档原则

新主系列全部完成并通过审核前，不删除或移动现有正式稿和 `research/`。

完成后整理为：

```text
archive/
  previous_series_2026-08-18/   # 旧 06-12 正式稿
  research_2026-08-18/          # 研究章程、trace、模块研究和实验记录
```

归档要求：

- 保留原文件名和内容，避免失去证据链。
- 添加归档 README，说明来源、固定 commit、归档日期和替代阅读入口。
- 主 README 和新正文不得链接归档文件作为正常阅读的必要步骤。
- `05_Enhancement.md` 是仍在使用的扩展教程，不进入历史归档。

## 4. 最终验收

归档完成后统一检查：

1. 根 README 和 Harness README 的所有主系列链接存在。
2. 06-12 的上一篇、下一篇导航形成完整链路。
3. 附录能够追溯关键术语和源码证据。
4. 旧正式稿与研究材料均已归档且无丢失。
5. Git diff 不包含用户原有改动之外的意外删除。
