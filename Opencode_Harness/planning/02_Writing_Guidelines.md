# Harness 系列写作规范

## 1. 每篇固定学习结构

每篇正文依次完成：

1. 用一个初学者能够理解的问题开场。
2. 在三到五句话内给出最短答案。
3. 给出本篇最小心智模型或小图。
4. 继续推进统一的“从零学习 Harness”场景。
5. 解释设计要解决的问题和职责边界。
6. 对应到 OpenCode 当前默认实现。
7. 说明失败、安全限制和常见误解。
8. 必要时用一个短小节说明 native V2 的变化。
9. 用“本篇掌握要点”收束。
10. 在文末给关键源码入口，不在正文中堆叠行号。

## 2. 三层表达

每个重要机制都按三层表达：

```text
通用 Agent 原理
-> OpenCode 中的具体实现
-> 源码和测试证据
```

不能直接从抽象定义跳到代码，也不能只讲通用 Agent 概念而没有 OpenCode 依据。

## 3. 语言要求

- 面向第一次系统学习 Harness 的读者，先用普通语言解释，再给术语。
- 首次出现采用“中文解释（English Term）”，代码标识保持原文。
- 一个段落只承担一个主要判断。
- 避免把“智能”“记忆”“自主”等拟人化表达当作精确实现结论。
- 不使用“完全解决”“始终保证”等超出证据的绝对表述。
- 不在正式正文中出现研究任务编号、Agent 工作记录或内部验收过程。

## 4. 示例要求

- 统一使用零基础读者学习 Harness 的场景。
- 优先演示读取教程、查看规则、了解工具、观察 Session 等低风险操作。
- 每个示例必须服务于当前章节问题，不为展示命令而展示命令。
- 示例中的项目路径、Session ID、模型名和配置值应明确标为示例。
- 涉及写入、Shell 或外部服务时，解释 Permission 和副作用边界。

## 5. 图表与源码

- 总览图只保留稳定角色和关键箭头。
- 时序图用于解释一轮或多轮执行，不混合当前默认路径与 native V2。
- 每张图前说明读图目标，图后解释关键转折。
- 源码片段通常不超过 25 行，只展示证明机制所需的部分。
- 文末源码索引至少包含文件、函数或导出符号和固定 commit。
- 行号可能随代码变化，不作为正文阅读的主要锚点。

## 6. 篇幅与重复控制

- 06 最短，只建立地图。
- 07-12 每篇围绕一个问题，不追求覆盖相邻章节的全部内容。
- 同一完整流程只在 07 展开；其他篇从自己的模块切入并链接 07。
- 同一张大型 V1/V2 对照表只保留一份。
- 每篇开头不重复长篇定义 Harness，使用一两句回扣即可。
