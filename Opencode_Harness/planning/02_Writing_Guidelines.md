# Harness 系列写作与信息编排规范

## 1. 目标不是减少内容，而是降低读者的组织负担

文章可以详细，也可以很长。需要避免的是地位不明、篇幅相近的平铺章节，而不是标题本身。作者必须先判断内容之间的真实关系，再选择表达结构。

每篇只回答一个中心问题，但不限制二级标题数量。一个需要独立建立认知、包含多项下级机制或承担明显叙事转折的主题，可以成为二级标题；它内部的组成、步骤、分支和源码解释使用三级标题继续展开。

主系列 06-12 鼓励使用二级、三级和必要的四级 Markdown 标题建立清楚层级。编号与标题层级保持一致：二级标题使用“一、二、三”，三级标题使用 `1.1`、`1.2`，四级标题使用 `1.1.1`、`1.1.2`。同一级编号必须从 1 开始并在所属父级内连续，三级和四级编号的前缀必须分别对应当前二级和三级标题。不要因为担心标题多而把多个独立机制挤进一个超长章节，也不要把只有一段补充说明的细节抬升成二级标题。

开篇的提问、直观答案和导语可以直接放在第一个二级标题之前，不需要为了形式增加“写在前面”等未编号 H2。一旦使用 Markdown 标题，该标题就必须进入连续编号树；正文中引用“第 4.2 节”等内部章节时，也必须在改动标题后同步核对编号与实际标题。

当一个 `1.1` 小节同时包含多条独立入口、多个控制阶段或不同事实边界时，应继续拆成 `1.1.1`。四级标题同样需要表达两个或更多真正可区分的下级内容；如果只有一个下级标题，应取消这个孤立 H4，把内容直接放回 H3。普通解释段落、同一判断的例子和简短注意事项不必为了编号而单独设标题。

## 2. 四种关系使用四种结构

### 有先后顺序

使用流程图、编号步骤或时间线。例如 Tool 生命周期应写成：

```text
注册 -> 本轮物化 -> Tool Call -> 验证 -> Permission -> 执行 -> 结算
```

各阶段可以详细解释，但应作为同一条主流程的下级内容，不能伪装成七个互不相关的一级主题。

### 地位并列

使用项目符号、并列表格或同一父标题下的三级标题。例如 System、Messages、Tool definitions 是 Provider Request 的三条并列输入通道。

只有需要逐字段比较时才使用表格。能用两三句话说明的并列关系，不为形式完整额外造表。

### 只能选择一种

明确写成“方案 A / 方案 B / 方案 C”，并说明选择条件。例如默认本地、监听模式、远程 attach 是运行拓扑的三种方案，不是需要依次执行的三个步骤。

### 从属或补充

放在所属主题内部，用段落、提示框或三级标题说明。常见误解应在第一次讲到机制时就地纠正；少见边界放在相关段落末尾，不单独升级为主要章节。

## 3. 详略由教学重要性决定

核心因果链必须充分回答：为什么需要该模块、输入是什么、源码怎样处理、产生什么输出、输出怎样影响下一阶段，以及容易混淆的相邻概念有什么区别。关键机制可以连续使用通俗解释、全景图、流程图、关键代码、逐段分析和设计取舍来展开，不设置统一篇幅上限。

重编排原则上保留旧稿中有教学价值的事实与边界。删除的对象应是重复总结、研究过程和无关支线，而不是为了减少编号而删除机制说明。若旧稿中的关键信息位置不合理，应移动或重写；需要让因果关系更完整时，鼓励补充解释和源码。

以下内容默认简写，并链接附录或归档：

- 与主线无关的完整测试清单和逐条运行日志；
- 少见 Provider 或 Plugin 分支；
- 不影响当前主线的 native V2 parity；
- 研究过程、实验数字和未决审计问题；
- 已在其他主讲章节完整解释的机制。

“简写”不是删除事实，而是把次要细节放到读者需要时能够查询的位置。直接支撑本篇核心机制的源码文件、函数和短代码片段应进入正文，不能全部推到附录。

## 4. 每篇只编排一次

推荐结构不是固定模板，可根据文章主题增加或合并模块，但通常包含：

1. 用一个具体问题开场，并在连续正文中给出直观答案。
2. 用通俗类比和全景图建立整体认知。
3. 按真实关系拆解主要模块、阶段或控制分支。
4. 对每个核心机制给出 OpenCode 关键源码并逐段解释。
5. 单列确有教学意义的边界、设计取舍和易混概念。
6. 给出源码文件索引，方便继续阅读。
7. 用一次简洁总结收束全文。

不要同时设置“最短答案”“心智模型总结”“常见误解”“掌握要点”“最终总结”五套重复结构。全文只需要一次正式收束；已经在正文就地解释的误解不在结尾重新列一遍。

## 5. 讲解文章的展开方式

概念解释优先采用：

```text
直观定义 -> 核心机制 -> 必要例子或对比 -> OpenCode 实现
```

详细机制优先采用：

```text
通俗解释
-> 架构或流程全景
-> 关键源码
-> 逐段解释
-> 与相邻机制的关系
-> 设计意义和边界
```

主系列正文不设置“动手实践”“请执行以下 Prompt”“预期观察”“完成条件”等任务型章节。案例只用于解释机制，不要求读者暂停阅读并操作 OpenCode。

## 6. 通用原理、当前实现与证据的层级

每个核心机制仍需完成三层映射：

```text
通用 Agent 原理
-> OpenCode 当前默认实现
-> 源码和测试证据
```

第三层必须服务于正文主线。正文保留理解机制所需的关键函数、控制结构和短代码片段，并解释代码怎样支持前面的架构结论；完整测试矩阵和跨文章索引再统一链接 `appendices/Source_Index.md`。

当前默认 TUI 路径是叙事主线。native V2 只有在改变当前概念边界时才用一段说明；完整架构演进集中在第 12 篇。

## 7. 语言、示例与图表

- 面向第一次系统学习 Harness 的读者，先用普通语言解释，再给术语。
- 首次出现采用“中文解释（English Term）”，代码标识保持原文。
- 一个段落承担一个主要判断，段落之间形成明确因果或转折。
- 示例统一使用零基础读者学习 Harness、读取教程和项目规则的低风险场景，但只作为讲解中的运行轨迹，不写成读者任务。
- 总览图只保留稳定角色；流程图解释顺序；表格只做真正的重复字段比较。
- 不使用“完全解决”“始终保证”等超出证据的绝对表述。
- 正文不出现研究任务编号、Agent 工作记录或内部验收过程。

## 8. 篇章之间的去重

- 06 只建立地图，不替专题文章预讲完整实现。
- 完整 Agent Loop 只在 07 展开。
- Context 可见性由 08 主讲；保存与恢复由 10 主讲。
- Tool 生命周期与 Permission 只在 09 展开。
- Agent、Plan、Todo、Task、Subagent 由 11 主讲。
- Runtime 拓扑与完整 current/native V2 演进由 12 主讲。
- 其他文章需要这些概念时，用一句接口说明和链接连接，不复制整段流程。
