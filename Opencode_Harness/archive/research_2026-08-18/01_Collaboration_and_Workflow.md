# OpenCode Harness 协作与研究流程

## 1. 协作角色

研究采用 4 个 Subagent、1 个总协调者和 1 个人类理解验收者。

| 角色 | 主要职责 | 主要研究产物 |
| --- | --- | --- |
| Subagent A：Agent 与 Orchestration | 追踪主循环、Provider Turn、Plan/Build、Todo、Task、Subagent、Retry、Interrupt 和停止条件 | Agent 与执行链研究笔记 |
| Subagent B：Context 与 Persistence | 研究 System Context、Instruction、Session History、Message/Part、Compaction、Pruning、Snapshot 和恢复 | Context 与状态研究笔记、07 术语候选 |
| Subagent C：Tools 与 Security | 研究 Tool Registry、工具物化、Permission、执行生命周期、输出边界及 MCP/Plugin 接入位置 | Tool 与安全边界研究笔记 |
| Subagent D：Runtime Boundary 与审计 | 研究 Client/Server、HTTP/SSE、Provider、事件和内部部署边界，并交叉检查 A/B/C 的结论 | Runtime 边界研究笔记、冲突报告 |
| 总协调者 | 固定范围、分配问题、统一术语、解决冲突、设计讲解、整合 06 及后续专题 | 总体调用链、状态矩阵、正式文档 |
| 用户 | 提出问题、进行 Teach-back、选择关键译法、检查解释是否真正可理解 | 理解反馈、术语决策、章节验收 |

不按“一个 Agent 读一篇文章”分工。五篇知乎文章是同一作者的一套系列资料，应该按模块拆分其中的主张，再由对应源码研究者验证。

## 2. 文件所有权

- Subagent 只修改分配给自己的研究笔记。
- 多个 Subagent 不同时修改 `06_Harness.md` 或后续正式专题文档。
- 06 及后续专题由总协调者在模块结论通过核对后统一编写。
- 尚未验证的结论写入研究笔记或 Open Questions，不直接进入正式文档。
- 用户正在修改的文件不得被 Subagent 覆盖或回退。

## 3. 研究阶段

### 阶段 0：冻结基线

1. 记录仓库分支、commit、产品包版本和工作树状态。
2. 建立来源清单。
3. 固定 V1/V2 状态标签和引用格式。
4. 确认 06 只讨论 OpenCode 内部 Agent Harness。

产物：项目章程、证据规则、来源清单。

### 阶段 1：建立总体执行链

从当前真正使用的入口追踪一次完整请求：

```text
用户输入
-> Client/Server 接收
-> Session 创建或恢复
-> Agent 与 Model 选择
-> Context 和工具组装
-> Provider Turn
-> Tool 授权与执行
-> Message/Part 或事件持久化
-> 继续、压缩或停止
-> Client 收到更新
```

这一阶段先建立骨架，不追求穷尽每个实现细节。

核对点：用户能够指出每一步由哪个层负责，以及哪些步骤可能重复。

### 阶段 2：按模块深入源码

Subagent A、B、C 并行研究，Subagent D 研究 Runtime 边界。每个模块必须完成：

1. 阅读通用概念资料，形成待验证问题。
2. 找到当前旧运行时入口与核心实现。
3. 找到对应 V2 实现、规格和状态表。
4. 查找测试，确认边界条件。
5. 必要时设计最小运行实验。
6. 记录 V1/V2 的差异和 V2 的改进目标。
7. 生成供用户理解检查的问题。

### 阶段 3：交叉审计

Subagent D 和总协调者检查：

- 是否只找到代码定义，却没有确认入口接线。
- 是否把目录名或类型名当成运行状态证据。
- 是否把 V2 规格中的计划写成已完成功能。
- 是否把 Permission 误写成操作系统 Sandbox。
- 是否混淆 System Context、Session History、Memory 和持久化存储。
- 是否混淆 Tool、MCP Server、Skill 和 Subagent。
- 是否忽略失败、取消、重试、恢复和并发边界。

### 阶段 4：最小实验

优先复用已有测试和 Recorded Provider。只有代码、规格和测试仍无法确定时，才运行隔离实验。

实验必须：

- 使用临时项目或可丢弃数据。
- 记录命令、环境、commit 和预期结果。
- 避免真实密钥和不必要的付费调用。
- 不在主项目中执行破坏性操作。
- 同时记录成功结果与失败结果。

### 阶段 5：用户理解核对

每完成一个模块，先进行讨论和 Teach-back，再开始正式写作。

建议的核对方式：

1. 总协调者用一张图和一个具体例子讲解。
2. 用户不用原文，按自己的理解复述。
3. 用户指出仍然模糊的术语或步骤。
4. 未讲清的问题进入 Open Questions。
5. 只有能清楚解释的内容才进入正式章节。

### 阶段 6：整合 06 和后续专题

1. 先确认完整大纲和每节证据覆盖。
2. 编写一个困难章节作为样例。
3. 核对术语风格和 V1/V2 标签。
4. 编写 06 总览和专题索引。
5. 根据模块研究分别完成 07 及后续专题文档。
6. 最后进行引用、链接、版本和事实审计。

## 4. 单个模块的完成条件

一个模块只有同时满足以下条件才算完成：

- 有清楚的概念定义。
- 有当前实现的入口和核心源码，并记录文件位置、所在函数或方法、行号和 commit。
- 有至少一个相关测试，或说明为什么没有找到测试。
- 有 V2 对应实现或明确的 `missing` 状态。
- 有 V1/V2 差异总结。
- 有尚未确定问题的显式记录。
- 用户能够复述主要流程。
- 可以转化为 06 中的具体章节，而不是源码文件清单。

## 5. 变更管理

- 每次开始新一轮源码研究前检查 HEAD。
- HEAD 变化时，不静默更新引用。
- 小范围变化记录新旧 commit 和受影响模块。
- 大范围变化重新冻结研究基线。
- 正式文档必须注明核对的 OpenCode commit 和日期。
